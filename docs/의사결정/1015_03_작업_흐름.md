# 1015_03 작업 흐름: 작업 단위 브랜치와 기록

- 상태: 확정 (사용자 결정, 2026-10-15)

## 배경

마감이 짧고(목표 10-16), 면접에서 "어떻게 만들었는가"를 설명해야 한다. 사용자 판단이 필요한 지점과 코드 작업을 구분하고, 각 단계를 나중에 따라갈 수 있게 남기기로 했다.

## 결정

1. **작업 단위마다 브랜치.** 브랜치 이름은 `종류/내용`(예: `setup/project-base`, `feat/tools`). 단위가 끝나면 **전체 점검**(README 폴더 구조·실행 방법·현재 상태, `진행_과정.md`, HANDOFF, 문서끼리 어긋남)을 하고 커밋할 파일 목록을 보고한다
2. **사용자 판단이 필요한 지점에서 멈춘다.** 모델 선택, 첫 실제 API 호출(비용 발생), 평가 기준처럼 결과를 좌우하는 선택은 선택지·근거를 정리해 묻고, 결정을 `docs/의사결정/`에 남긴다
3. **단계별 길잡이는 `docs/진행_과정.md` 한 곳.** 단계마다 무엇을·어떻게·왜를 짧게 쓰고 자세한 근거는 의사결정 문서로 연결한다(빌라 시세 저장소와 같은 방식)
4. 커밋·푸시는 **사용자가 요청할 때만** 한다
5. 푸시는 의미 있게 완성된 묶음 단위로 한다. 앞으로 계속 바뀔 문서(README·진행 과정 등)를 고칠 때마다 올리지 않는다. 이력으로 남길 가치가 있는 것은 판단이 바뀐 지점(예: 1차→2차 채점 사이의 수정)이다

## 결과

- `setup/project-base`(PR #1)는 점검 없이 커밋·푸시됐다(AI가 "진행할까?"를 승인으로 오해). README에 폴더 설명이 빠졌고 이 문서의 커밋 규칙 문장이 틀린 채로 올라갔다 → 사용자가 지적, 위 4·5번을 추가. 빠진 것은 다음 묶음에서 함께 반영
